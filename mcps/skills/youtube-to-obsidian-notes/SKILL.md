# YouTube → Obsidian Revision Notes

## 1. Purpose

Turn a YouTube video's transcript into notes that are:

- accurate to the source
- conceptually organized
- easy to understand
- easy to revise
- easy to recall later
- integrated with the user's existing Obsidian vault

The goal is **understanding + durable recall**, not transcript compression.

Do not merely summarize the video chronologically.

---

## 2. Priority Order

When instructions conflict, use this priority:

1. Explicit user request
2. Existing vault rules and conventions
3. Transcript/source fidelity
4. Examples, analogies, demonstrations, and mental models
5. Conceptual organization
6. Revision and active recall
7. Obsidian formatting preferences
8. Brevity

A shorter note is not better if important understanding or memory anchors were removed.

---

## 3. Core Workflow

Follow this sequence:

1. Identify the YouTube source.
2. Retrieve the transcript using the existing YouTube transcript MCP/Skill.
3. Retrieve the complete transcript before writing notes whenever possible.
4. Determine the video's main subject, scope, and intended learning outcome.
5. Inspect the Obsidian vault for applicable rules, templates, related notes, MOCs, properties, tags, and naming conventions.
6. Understand the transcript as a whole.
7. Extract concepts, relationships, examples, caveats, procedures, and mental models.
8. Organize the material into a coherent knowledge structure.
9. Connect it to relevant existing vault knowledge.
10. Write the note using appropriate Obsidian formatting.
11. Add revision/active-recall material.
12. Validate accuracy, completeness, links, formatting, and vault compliance.
13. Save only after validation.

Do not start drafting the final note after reading only a fragment of the transcript unless the user explicitly asks for a partial result.

---

# 4. Transcript Retrieval

Use the existing YouTube transcript capability available in the environment.

Do not assume a specific MCP tool name if the environment exposes it under a different name. Inspect the available tools/Skill instructions when necessary.

### Retrieval rules

- Prefer manually created captions when available.
- Auto-generated captions are acceptable when that is the only usable source.
- Preserve the source language unless the user requests another language.
- Retrieve the full transcript when possible.
- Do not silently omit sections because they appear repetitive.
- If the transcript is unavailable, incomplete, or corrupted, state that clearly.
- Never invent missing transcript content.

The transcript is the primary source for claims about what the speaker said.

---

# 5. Source Fidelity

The note should accurately represent the video's content.

### Preserve

- definitions
- explanations
- reasoning
- cause/effect relationships
- conditions and exceptions
- assumptions
- procedures
- important terminology
- warnings and caveats
- conclusions
- examples
- demonstrations
- analogies
- stories when they explain the idea
- numerical examples
- code examples
- counterexamples
- comparisons
- mental models

### Do not

- add unsupported claims
- change the speaker's meaning
- turn speculation into fact
- remove important qualifications
- manufacture examples
- present outside knowledge as if it came from the video

If the speaker is uncertain or makes a qualified claim, preserve that uncertainty.

---

# 6. Examples Are Part of the Knowledge

**Meaningful examples are not decoration. They are memory anchors.**

When the speaker uses an example to explain a concept, preserve it when it contributes to understanding or recall.

Examples may include:

- real-world situations
- analogies
- metaphors
- stories
- demonstrations
- numerical examples
- code snippets
- thought experiments
- counterexamples
- before/after comparisons
- visual descriptions

### Placement

Keep an example close to the concept it explains.

Do not collect all examples in an unrelated appendix merely to shorten the main explanation.

### Example transformation

Prefer:

> **Concept:** Stateless API  
> **Example from the video:** Each request contains everything the server needs, so the server does not need to remember the client's previous request.

over deleting the example and retaining only the definition.

### Speaker vs generated examples

Clearly distinguish:

- **Example from the video**
- **Analogy from the video**
- **Additional example** — generated by the assistant

Never make an assistant-generated example look like something the speaker said.

See `references/examples-and-memory.md` for detailed rules.

---

# 7. Understanding Before Summarizing

Before writing, build an internal model of the material.

Identify:

- What is the central idea?
- What concepts support it?
- How do the concepts relate?
- What problem is being solved?
- Why does the idea matter?
- What assumptions are involved?
- What examples make it intuitive?
- What common misunderstandings are addressed?
- What should the learner remember later?

Prefer a conceptual hierarchy over the video's exact speaking order.

A useful transformation is:

```text
Video sequence
    ↓
Understand
    ↓
Concept hierarchy
    ↓
Relationships
    ↓
Examples / mental models
    ↓
Revision structure
```

---

# 8. Note Structure

Choose the structure based on the material rather than blindly applying one template.

A typical learning note can contain:

1. Title
2. Source / metadata
3. One-paragraph overview
4. Core idea
5. Key concepts
6. Concept relationships
7. Detailed explanations
8. Examples / analogies / mental models
9. Procedures or implementation details
10. Caveats / edge cases
11. Common mistakes or misconceptions
12. Practical takeaways
13. Active recall questions
14. Related notes

Do not create empty sections just to satisfy a template.

See `references/note-patterns.md`.

---

# 9. Optimize for Recall

A good note should help the user reconstruct the idea later without replaying the video.

Use:

- concise explanations
- meaningful headings
- conceptual grouping
- comparisons
- examples
- mental models
- cause → effect relationships
- selective emphasis
- recall questions
- "why" explanations
- "when to use this" information where relevant

Avoid:

- walls of prose
- transcript-like repetition
- excessive bullet fragmentation
- unnecessary bolding
- trivia that does not aid understanding

### Active recall

Questions should test understanding, not merely recognition.

Prefer:

- Why does X happen?
- How does X differ from Y?
- What would happen if X changed?
- When would you use X?
- Explain X using the example from the video.
- What assumption does X depend on?
- What mistake would produce Y?

Use example-based recall when examples are central to the concept.

---

# 10. Vault Integration

Before creating or editing a note, inspect the relevant vault context.

Look for:

- global vault instructions
- folder-specific rules
- templates
- nearby notes
- existing notes on the same topic
- MOCs / indexes
- properties
- tags
- naming conventions
- linking conventions

**Vault-specific rules override generic formatting preferences in this Skill.**

Do not create a new note when an existing note should be updated, unless the vault rules or user request indicate otherwise.

Avoid duplicate concepts.

Reuse established terminology and note structures when appropriate.

---

# 11. Wikilinks

Use Wikilinks to connect meaningful concepts already present or clearly appropriate for the vault.

Good links:

- established concepts
- related subjects
- prerequisite knowledge
- important technologies
- recurring topics
- relevant MOCs

Avoid:

- linking every noun
- creating links merely for visual density
- inventing pages without reason
- changing established vault terminology unnecessarily

If a useful concept does not have an existing note, follow the vault's conventions for whether to create or suggest one.

---

# 12. Obsidian Formatting

Follow existing vault conventions first.

Use formatting for meaning, not decoration.

Potential tools include:

- headings
- bullet/numbered lists
- tables
- callouts
- code blocks
- LaTeX
- Wikilinks
- tags
- properties
- Mermaid

Do not use every feature simply because it is available.

Use tables when comparing structured attributes.

Use code blocks for actual code or syntax.

Use LaTeX for mathematical notation where it improves precision.

Use callouts selectively for important warnings, insights, definitions, or takeaways.

See `references/obsidian.md`.

---

# 13. Mermaid

Use Mermaid only when a diagram materially improves understanding.

Good uses:

- processes
- workflows
- system architecture
- dependencies
- decision trees
- state transitions
- relationships between concepts
- pipelines

Avoid Mermaid for simple lists or relationships that are clearer in prose.

Keep diagrams readable and not unnecessarily elaborate.

Ensure Mermaid syntax is valid.

---

# 14. External Knowledge

The transcript is the source of truth for the video's content.

External knowledge may be used when necessary to:

- clarify terminology
- correct an obvious transcription issue
- provide minimal context
- verify a factual claim when verification is important

When external information materially changes or extends the video's content:

- distinguish it from the speaker's content
- do not attribute it to the speaker
- preserve the distinction in the note

If the user asks for pure transcript-based notes, do not add external information.

---

# 15. Accuracy and Uncertainty

Never fabricate:

- quotes
- timestamps
- examples
- statistics
- citations
- claims about the speaker
- source details

If timestamps are available, use them selectively for important sections.

Do not create a timestamp merely because the note would look better with one.

If transcript wording is ambiguous, prefer a cautious interpretation and mark uncertainty when it matters.

If a technical statement appears incorrect, do not silently rewrite the speaker's claim as though that was what they said.

You may add a clearly distinguished correction/context section when useful and permitted by the user's request.

---

# 16. Compression Rules

Compress repetition, not understanding.

You may combine:

- repeated explanations
- filler
- conversational transitions
- redundant wording
- repeated examples that add no new information

Do not compress away:

- the first useful explanation
- the clearest example
- a critical caveat
- an important exception
- the reasoning behind a conclusion
- a mental model
- a demonstration that makes an abstract idea concrete

The objective is **high information density without losing the learning path**.

---

# 17. Quality Standard

Before saving, verify:

### Source
- Was the transcript retrieved?
- Was enough of the transcript read to understand the whole topic?
- Are source claims represented accurately?

### Knowledge
- Is the central idea clear?
- Are important concepts present?
- Are relationships between concepts clear?
- Are important caveats preserved?

### Examples
- Were meaningful speaker examples preserved?
- Were analogies and mental models retained?
- Are generated examples clearly labeled?

### Recall
- Can the learner understand the topic without replaying the video?
- Are there useful active-recall questions?
- Do examples help reconstruct the concept?

### Vault
- Were applicable vault rules inspected?
- Is the note consistent with existing conventions?
- Were existing related notes considered?
- Are Wikilinks meaningful?
- Were duplicate notes avoided?

### Formatting
- Is the hierarchy readable?
- Is Mermaid actually useful?
- Are tables/code/LaTeX used appropriately?
- Is metadata consistent with the vault?

### Integrity
- No hallucinated facts
- No fabricated timestamps
- No fabricated quotes
- No invented source content
- No accidental attribution of generated material to the speaker

---

# 18. Final Principle

Create notes that make the learner think:

> "I understand this, I can explain it, and I can reconstruct it later."

Optimize for **understanding, structure, examples, mental models, and recall**.

---

# 19. Visual Detection & Extraction

The transcript predicts where useful visuals may occur. Do not rely solely on explicit verbal cues. Look for both explicit and conceptual signals:

**Explicit Verbal Cues:**
- "as you can see..."
- "look at this diagram..."
- "on the screen..."
- "this architecture..."
- "this table..."

**Conceptual Cues (Proactively check for visuals here):**
- Step-by-step walkthroughs or examples (e.g., "Let's take 1 2 3 4 as a sequence").
- System architecture discussions (e.g., "Where do you place the cache?").
- Comparisons, formulas, or lists being formulated.
- Any time a complex relationship is explained, the presenter is likely drawing it.

When any of these cues are found and correspond to an **Essential** or **Helpful** visual (e.g., architecture diagrams, important tables, mental models):
1. Identify the exact timestamp directly from the transcript (ensure the transcript tool was called with `include_timestamps=True`).
2. Read the instructions in the `youtube-visual-extraction` skill to learn how to search for, verify, and extract the best frame from the video using a narrow time window.
3. Integrate the resulting saved screenshot naturally into the note.
4. Keep the visual right next to the concept or example it illustrates.
5. Provide the timestamp in the visual metadata.
6. **Obsidian Auto-Rename Warning:** Obsidian often automatically appends timestamps to new image files. Always verify the exact filename in the vault directory before embedding the `![[image.png]]` link, otherwise the link will break.

Example:
```markdown
### Visual Explanation
![[<note-name>-<timestamp>.png]]

> [!note]
> The diagram shows...

[Video — <timestamp>](YOUTUBE_URL&t=X)
```

Never capture Decorative visuals (e.g., presenter face, transition animations, title cards). Avoid unnecessary screenshots; a typical video might have only 0-5 useful visuals.

# 20. Handling Long Videos

When processing videos that are longer than 20-30 minutes (where the transcript is massive and risks exceeding context window limits or causing dropped information):

1. **Chunking:** Do not attempt to process the entire transcript and output the entire note in a single step.
2. **Iterative Processing:** Divide the transcript into logical chunks (e.g., using timestamps or major topic shifts).
3. **Sequential Summarization:** Read a chunk, extract the notes/visuals for that chunk, and write them to the markdown file before moving on to the next chunk.
4. **Append, Don't Rewrite:** Use the `multi_replace_file_content` or `write_to_file` tools to continuously append new sections to the final note as you progress through the transcript.
5. **Subagents:** If the video is extremely long (e.g., a 2-hour lecture), consider spawning subagents to process different chunks of the transcript concurrently or sequentially, and then synthesize their outputs.
